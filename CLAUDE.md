@AGENTS.md

## What this repo is

`orbita-front` is the dashboard frontend for Órbita: a multi-tenant conversational CRM (WhatsApp + Instagram, TikTok in phase 1) with AI agents. **ORB-D01** landed the design system, authenticated shell, cookie-based API client, and login/register. **ORB-D04** adds pipeline/stage management on `/t/[tenantId]/pipeline`. Inbox, contacts, and the kanban cards (D05) are still placeholders.

The authoritative domain/data model lives in the sibling `docs` folder at `../docs/orbita-schema.dbml` (this repo doesn't include it — read it directly from that path). It describes a multi-tenant CRM: tenants → conversations/messages (WhatsApp/Instagram) → deals/pipelines, plus an AI-agent layer and an append-only events log. Any screen that lists or mutates domain data should be built against that model, not against ad-hoc shapes.

The backend API is a separate sibling repo (`../Orbita`, ASP.NET Core) — see its own `CLAUDE.md` for its conventions and architecture; the two must agree on contracts.

## Commands

- Dev server: `bun dev`
- Build: `bun run build`
- Start (prod build): `bun run start`
- Lint: `bun run lint` (ESLint 9 flat config: `eslint-config-next` core-web-vitals + typescript)
- Type-check: `bunx tsc --noEmit`
- Unit tests: `bun run test` (Vitest + Testing Library)
- E2E: `bun run test:e2e` (Playwright)
- API types: `bun run generate:api` (from `openapi/orbita.json`; refresh snapshot with `bun run refresh:openapi`)

Package manager is **bun** (`bun.lock`, `packageManager: bun@1.4.0` pinned in `package.json`) — always use `bun`, never `npm`/`yarn`/`pnpm`, to keep the lockfile consistent.

## Architecture

- Next.js 16 App Router (`app/`), React 19, TypeScript 5 with `strict: true`, Tailwind CSS 4 via `@tailwindcss/postcss`, path alias `@/*` → repo root (`tsconfig.json`).
- Route groups: `(marketing)` public stub, `(auth)` login/registro/recuperar, `(app)` authenticated shell under `/t/[tenantId]/…`. Tenant id is always in the path; the JWT has no tenant claim.
- HTTP access goes through `lib/api/client.ts` (`credentials: "include"`, 401 → `POST /api/auth/refresh`). Types come from `lib/api/generated/schema.d.ts` (generated; do not edit).
- `AGENTS.md` (imported above via `@AGENTS.md`) is regenerated by `next dev` itself on every run — it documents that this Next.js version may diverge from training-data assumptions and points at `node_modules/next/dist/docs/` for the current APIs. Don't strip it from a diff (it just comes back); read the referenced docs before relying on App Router behavior that might have changed.
- ESLint config is the flat-config format (`eslint.config.mjs`, `defineConfig([...])`) extending `eslint-config-next`'s `core-web-vitals` and `typescript` presets — add project rules there, not a legacy `.eslintrc`.

## Mandatory engineering conventions

1. **SOLID, applied to frontend terms.** Components, hooks, and data-fetching services each own one responsibility. Depend on typed interfaces (props, hook return types, API response types) at the boundary between UI and data access — don't scatter raw `fetch` calls through components.
2. **Ultra-strict typing.** `strict: true` stays on. **Never use `any`** — use `unknown` with narrowing, generics, or a proper domain type instead. No `@ts-ignore`/`@ts-expect-error` without a comment justifying why. Every prop, hook return value, and API response must carry an explicit type, never an inferred `any`.
3. **Nothing ships untested.** Every feature (component, hook, page) lands with tests in the same set of commits as the feature itself.
4. **Commit checkpoints.** Format `<type>: <short imperative description>`, max 72 characters, English only. Types: `feat`, `fix`, `refactor`, `chore`, `test`, `docs`, `style`. One logical unit of work per commit — split anything that needs "and" in the message. Don't let more than ~2 hours of work sit uncommitted. **Never add a `Co-Authored-By`, `Claude-Session`, or any other AI/tool attribution trailer to a commit message in this repo** — the author is the human contributor, full stop.
5. **Branching.** `feature/<short-descriptive-name>` from `develop`, merged back into `develop`; `hotfix/<short-descriptive-name>` from `main`, merged into both `main` and `develop`. Never branch a feature off another feature branch without explicit coordination.
   - **Current state:** `develop` exists; new work branches `feature/*` from `develop`.
